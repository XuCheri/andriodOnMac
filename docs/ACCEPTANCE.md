本轮在用户授予屏幕录制与辅助功能权限后，通过已安装的应用完成上述 USB 镜像、副屏和中文输入联调。首轮显示的约 8.7 秒包含人工确认配对，不能作为启动性能；后续副屏单次约 2.7 秒、4.5 秒同样包含连接过程，样本不足，不能据此判定首帧目标达标。约 56–58 fps、队列为 0 只是当时的真实 ACK 快照，精确端到端延迟、持续动态帧率、能耗与 30 分钟稳定性尚未验收。

Wi-Fi 扫码会话在拔掉 USB 后由用户确认画面与触控正常，管理界面也收到真实渲染 ACK。该次首帧读数约 81 秒包含扫码等人工等待，不能作为首帧性能证据；约 58 fps、队列为 0 同样只代表短时快照。连接流程没有将 Android 无线调试作为依赖，但未实测其开关是否关闭。

精确模式修复后另做了两次短时 helper 验证：1280 × 720 与 1920 × 1080 分别通过 TERM 退出，1920 × 1080 另通过 `--probe` 自动退出。三次均返回 0 并恢复只剩原主屏；主屏 ID、位置、逻辑尺寸及像素模式保持不变。该结果验证本机显示配置与回收，不替代修复后手机端的完整复测。

## 0.1.0：手机 → Mac 历史记录

下列结果来自旧方向及当时版本，保留供回归对照；尤其是 Android 无线调试自行关闭的问题，不应套用于新版 Mac → 手机扫码连接。

2026-10-19 实测环境：Mac mini（Mac14,3 / Apple M2 / 8 GB），macOS 26.4.1；Xiaomi 23117RK66C，Android 16（API 36）；USB 数据线连接。默认 H.264、长边 1920、60 fps 上限、8 Mbps；引擎报告 Metal 渲染和 VideoToolbox 硬件解码，实际编码画面 864 × 1920。构建工具为 CLT 26.6 / Swift 6.3.3。

用户已在实际手机窗口确认“画面正常，点击滑动也正常”。此前独立引擎运行约 6 分钟；这不等于完成 30 分钟稳定性测试。未记录可重复的首帧和操作延迟数据，不宣称达到 USB 3 秒 / Wi-Fi 5 秒或持续 60 fps 目标。

本机已通过 52 项 Swift Testing 测试（8 个套件）、SwiftPM release 构建、Shell/Python/C 检查、应用 ad-hoc 签名校验，以及 arm64 和系统动态依赖检查。测试包括设备与 mDNS 解析、参数隔离、配对码不进入 argv、设备身份/旧异步结果、有限重连、真实 ADB 启停、进程后代清理及 scrcpy 日志实时交付。GUI 实测曾暴露非终端 stdout 缓冲导致启动状态误报，已给 scrcpy stdout 单独配置 PTY，并增加真实 C stdio 回归；stdin 继续使用独立管道。另修复短命 ADB 命令退出后跨线程等待未返回的问题，改用启动前注册的退出回调；新增串行 100 次短命命令回归。

这些自动结果不替代未完成的真机项目。未完成最低支持版本 macOS 13 / 干净机器验证、全量第三方重建；ADB 精确构建源码对应关系的未核实范围见 [第三方源码说明](THIRD_PARTY_SOURCES.md)。
